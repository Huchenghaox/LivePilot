# 技术决策记录

## 2026-06-23：新增独立 Beta 应用目录

决策：不改造旧 `backend/`、`admin/`、`miniapp/` 业务，而是新增 `api/` 和 `web/`。

原因：

- 旧项目是商机/商品/订单/拍卖等业务，和 AI直播运营助手差异较大。
- 用户指定新技术栈为 Next.js + FastAPI。
- 保留旧代码可避免破坏历史资产。

## 2026-06-23：Phase 1 使用 Mock AI 适配层

决策：缺少模型 Key 时使用 Mock 适配层，并在结果中保留 `source: mock`。

原因：

- 需求要求缺少模型 Key 时使用 Mock 和环境变量。
- 不允许写死假结果冒充完成，因此所有模拟结果必须明确标记。

## 2026-06-23：本地开发支持 SQLite，生产保留 PostgreSQL

决策：FastAPI 数据层通过 `DATABASE_URL` 切换。未配置时使用本地 SQLite，Docker/生产使用 PostgreSQL。

原因：

- Phase 1 需要快速可运行闭环。
- 架构仍保持 PostgreSQL 兼容，不阻断后续部署。

## 2026-06-23：Phase 2 先落地上传与任务记录

决策：Phase 2 先完成音视频上传、文件记录和 `waiting` 任务创建，再接 FFmpeg、Celery 和 ASR。

原因：

- 上传是内容分析链路的入口，可独立验收。
- 文件类型、大小、安全文件名、权限校验和场次归属校验需要先稳定。
- 先持久化 `AnalysisJob` 能保证后续 Celery 接入时任务状态、重试和幂等有明确数据基础。

## 2026-06-23：FFmpeg 缺失时任务失败而不是接口崩溃

决策：当运行环境没有 `ffmpeg` 或 `ffprobe` 时，将处理任务标记为 `failed`，并返回中文安装说明。

原因：

- Beta 用户不应看到 Python 堆栈或底层命令错误。
- 任务状态持久化后，用户可以在安装 FFmpeg 后点击重试。
- 这与后续 Celery 异步任务模型兼容。

## 2026-06-23：ASR 不伪造说话人身份

决策：在没有可靠说话人分离能力前，转写片段的 `speaker` 统一标记为“未知”。

原因：

- 主播、连麦人和评论朗读内容不能凭空判断。
- 错误归因会影响复盘结论和合规判断。
- 后续可以在同一数据结构上增加人工修正和说话人分离结果。

## 2026-06-23：优先收缩为截图复盘 MVP

决策：暂停音视频、FFmpeg、ASR、说话人识别、连麦分析、实时助手、高光剪辑、动态背景和自动场控的继续开发与前台入口，优先完成“抖音后台截图复盘 MVP”。

原因：

- 截图复盘是当前最短可交付闭环。
- 用户已经验证注册登录可用，下一步应集中打磨上传截图、数据确认、复盘报告和下一场方案。
- 已完成的音视频基础代码保留，避免破坏已有工作，但不继续扩展。

## 2026-06-23：当前 MVP 仅暴露图片识别和文本分析模型用途

决策：模型设置页面和后端入参暂时只接受“图片识别”和“文字分析”。

原因：

- 当前主流程只依赖截图识别和报告生成。
- 音视频、ASR、图片生成相关能力已暂停，不应在普通用户入口制造可选项。
- 已完成的底层代码可以保留，后续恢复对应阶段时再开放模型用途。

## 2026-06-23：真实模型通过 OpenAI 兼容 HTTP 适配

决策：真实视觉模型第一版通过 OpenAI 兼容 HTTP 接口接入，不在业务路由中引入具体厂商 SDK。

原因：

- 用户需要支持平台模型和自带 API Key，OpenAI 兼容接口能覆盖更多供应商。
- 业务代码只依赖统一适配层，后续替换模型供应商不会影响上传、确认和报告流程。
- Mock 适配器与真实适配器保持同一结构化输出，便于测试和缺 Key 时兜底。

## 2026-06-23：文字模型与图片模型独立配置

决策：文字分析模型和图片识别模型完全独立配置。当前默认文字模型使用 `glm-5.1`，图片识别模型不再默认使用 `glm-5.1`。

原因：

- 已验证当前渠道只暴露 `glm-5.1`，该模型可用于文本，但不是多模态视觉模型。
- 将非多模态模型标记为图片模型会误导用户和流程状态。
- 截图复盘在缺少视觉模型时仍可通过手动录入关键数据继续，不阻塞真实文字报告开发。

## 2026-06-24：规则库与模型能力分离

决策：新增“规则与运营提示中心”，并将规则库作为报告生成时的动态上下文，不把持续变化的平台规则写死在代码或固定 Prompt 中。

原因：

- 平台规则、治理重点和运营经验会持续变化，更换模型不能替代规则维护。
- 规则更新不需要重新训练模型；模型每次分析时读取当前有效规则。
- 报告必须保存当时使用的模型名称、Prompt 版本和规则版本快照，方便后续追踪。
- 规则来源需要分级：平台官方规则、主播个人提醒、系统提示和运营经验不能混写。
- MVP 阶段先用类型、范围、关键词和生效时间过滤，为后续 Embedding 语义检索预留边界。

## 2026-06-24：系统用户、主播档案和平台账号分离

决策：新增 `PlatformAccount` 及用户成员、主播绑定、授权、同步任务和数据快照模型；现有 `Streamer` 在当前代码中继续作为主播档案使用，后续文档称为 AnchorProfile。

原因：

- 一个系统用户可能管理多个抖音账号。
- 一个抖音账号可能由主播本人、运营人员或机构管理员共同管理。
- 一个主播档案可能绑定多个平台账号，并需要设置主要账号。
- 旧直播场次不应因缺少 `platform_account_id` 而失效。

## 2026-06-24：只预留官方抖音 OAuth，不做非官方接入

决策：当前只实现 Douyin OAuth Provider 接口和未配置状态，不实现 Cookie、账号密码、网页爬虫、模拟登录或逆向接口。

原因：

- 抖音账号授权和数据同步必须走官方能力和真实审批权限。
- 当前没有官方直播复盘数据权限时，截图上传和手动录入仍是正式可用路径。
- Token 必须后端加密保存，不返回前端、不写日志、不入 Git。

## 2026-06-24：默认采用深色直播生态视觉，但不冒充抖音官方

决策：Beta 默认采用深色主题，主色使用青蓝，辅助色使用玫红，营造直播和 AI 科技感；不使用抖音官方 Logo、官方专属图标、官方页面截图或完全一致的官方界面结构。

原因：

- 目标用户处在直播生态中，深色、高对比和轻微青红强调更贴近直播使用场景。
- 产品仍是独立直播运营工具，必须避免让用户误认为是抖音官方产品或官方授权产品。
- 当前先用全局 Token、共享组件和兼容层完成视觉底座，后续逐页细化首页、复盘、报告、规则和模型设置。
- 报告打印和保存 PDF 必须使用白底黑字，不能直接打印深色页面。
